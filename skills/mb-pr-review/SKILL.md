# ミライビルド PRレビュワー

## 概要

GitHub 上の PR またはローカルブランチ差分を対象に、コードレビューを日本語で行う。
対象リポジトリのガイドを先に読み、全変更ファイルを必須レンズで 3 パス確認してから、P0/P1/P2/P3 の重大度を付ける。

## 実行原則

- 既定ではレビュー専用として振る舞い、ユーザーが明示しない限りコード修正、整形、commit、push はしない。
- 出力は findings-first とし、指摘事項を重大度順に並べる。要約や良い点は指摘事項の後に置く。
- PR タイトル、PR コメント、レビューコメントを作る場合も日本語で書く。
- `P0` は現実的な到達経路があり、広範囲・不可逆・重大なセキュリティ影響が高い確度で起きる致命的問題に限定する。
- `P1` はビルド失敗、実行時エラー、通常経路の機能破壊、契約不整合など、具体的な破綻経路を示せる明確な不具合とする。
- `P2` は保守性、可読性、責務分離、テスト容易性、仕様追跡性の問題とする。
- `P3` は軽微な問題、表記ゆれ、コメント不足、将来対応、TODO 化すべき未実装箇所とする。
- 明らかに未実装で落ちる箇所は、それだけで `P0` や `P1` にしない。`P3` として「TODO コメントを書く」「未実装であることを明示する」などの指摘にする。
- コーディングガイド、`AGENTS.md`、`README`、`docs/` 配下の開発規約を必ず確認する。見つからない場合は「確認できたガイドなし」と明示する。
- 正しさ・契約、責務分離・依存境界、Readable Code、テスト容易性・規約の全レンズを必ず実行し、未実施の観点を残さない。
- 指摘候補を全レンズから集めた後に重大度を決める。重大度を探索観点として使わない。
- サブエージェントを利用できる場合は責務分離と Readable Code を別々に委譲し、主担当が正しさ・契約とテスト容易性を確認して統合する。利用できない場合は同じレンズを順番に実行する。
- 3 パスの最後に反証、重複排除、重大度の正規化を行う。再実行しても同じ指摘になるよう、ファイル順、差分順、根拠行を安定させる。
- 推測だけの指摘を避ける。証拠要件を満たさない候補は指摘から除外し、レビュー結論が変わる不明点だけを確認事項へ移す。

## 使う場面

- GitHub PR の URL、PR 番号、または `gh pr view` できる PR をレビューしたい。
- ローカルの作業ブランチと base ブランチの差分をレビューしたい。
- 変更内容について、明確な不具合、保守性、瑣末な改善を分けて指摘したい。
- 責務の混線、依存境界の崩れ、誤読を招く命名や制御フローを漏れなく確認したい。
- コーディングガイドとの不一致を含めて、漏れの少ないレビュー結果を出したい。

## 基本フロー

1. 対象 repo、base、head、PR URL を確定する。可能なら `scripts/collect_review_context.py` で差分、commit、コーディングガイド候補を read-only で棚卸しする。
2. [`references/review_workflow.md`](./references/review_workflow.md) を読み、GitHub PR とローカル差分のどちらの入口で進めるかを決める。
3. [`references/lenses/responsibility_separation.md`](./references/lenses/responsibility_separation.md) と [`references/lenses/readable_code.md`](./references/lenses/readable_code.md) を読み、必須レンズの完了条件を確定する。
4. コーディングガイド、プロジェクト固有ルール、変更差分、呼び出し元・呼び出し先・近接する既存実装を読む。
5. 変更ファイルを 3 パスで確認する。
   - 1 パス目: 全レンズで差分全体を走査し、重大度を付けずに候補を集める。
   - 2 パス目: レンズごとに関連実装と既存パターンを確認し、候補の根拠と影響を検証する。
   - 3 パス目: 全差分を再走査し、見落とし、反証、重複、変更範囲外の指摘を確認する。
6. [`references/severity_policy.md`](./references/severity_policy.md) を読み、検証済み候補だけに P0/P1/P2/P3 を付ける。
7. 指摘事項、観点別確認結果、確認事項、テスト実行有無、残リスクを日本語で返す。

## 出力ルール

- 指摘がある場合は、最初に `指摘事項` を出す。
- 各指摘は `P0` `P1` `P2` `P3` と主レンズで始め、根拠、観測した事実、影響、修正方向を含める。
- 行番号が取れない場合でも、差分内の関数名、コンポーネント名、設定名など、追跡できる根拠を示す。
- 指摘がない場合は「指摘事項はありません」と明記し、確認した範囲と残リスクを短く添える。
- 指摘の有無にかかわらず、各必須レンズの確認ファイル数、指摘件数、除外理由を `観点別確認結果` に記載する。
- 実行したコマンド、実行できなかった検証、依存関係や認証不足で諦めた確認は最後にまとめる。
- inline code comment directive は、ユーザーが明示的に求めた場合だけ使う。

## リソース

- [`scripts/collect_review_context.py`](./scripts/collect_review_context.py)
  - repo、base、head、変更ファイル、commit、コーディングガイド候補を read-only で棚卸しする補助スクリプト。
- [`references/review_workflow.md`](./references/review_workflow.md)
  - GitHub PR とローカルブランチ差分のレビュー手順、3 パスレビュー、再現性を保つためのルール。
- [`references/severity_policy.md`](./references/severity_policy.md)
  - P0/P1/P2/P3 のランク分け、マージ判断、未実装箇所の扱い、指摘の書き方。
- [`references/lenses/responsibility_separation.md`](./references/lenses/responsibility_separation.md)
  - 責務の混線、依存方向、所有権、副作用境界を確認する必須レンズ。
- [`references/lenses/readable_code.md`](./references/lenses/readable_code.md)
  - 命名、制御フロー、式、変数、コメント、テストの理解容易性を確認する必須レンズ。
