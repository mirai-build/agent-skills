# P1/P2/P3 重大度ポリシー

PR レビューでは、重大度を増やすことよりも、指摘の根拠と再現性を優先する。
迷う場合は、実害の具体性、影響範囲、修正しない場合の手戻りを順に確認する。

## 候補収集と重大度判定を分離する

P1/P2/P3 はレビュー観点ではなく、検証済み指摘の重大度である。
正しさ、責務分離、Readable Code、テスト容易性の各レンズから候補を集め、根拠と影響を検証した後にランクを決める。
探索中に「これは P3 だから後で見る」のような除外をせず、各レンズの確認を完了してから分類する。

## P1: 明らかな不具合やエラーの元

`P1` は、変更が取り込まれると実際に壊れる可能性が高く、具体的な破綻経路を説明できるものに限定する。

- 実行時例外、syntax error、型不整合、import 失敗、build 失敗が明確に起きる。
- API contract、DB schema、migration、認証認可、外部連携の不一致で既存機能が壊れる。
- データ破壊、情報漏えい、権限昇格、冪等性破綻など、影響の大きい安全性問題がある。
- 条件分岐、日付、ページング、非同期処理、transaction、cache などで、通常利用の結果が明らかに誤る。
- 追加・変更されたテストが必ず落ちる、または既存テストの前提を明確に壊している。

`P1` にするには、原則として「どの入力や経路で、どのファイルのどの処理が、どう壊れるか」を示す。
単なる懸念、好み、将来の拡張性だけでは `P1` にしない。

## P2: 保守性や可読性の問題

`P2` は、今すぐ壊れるとは限らないが、保守、変更、調査、テストを難しくする問題に使う。

- 責務が混線し、画面、feature、domain、shared、lib などの境界が崩れている。
- 依存方向、状態の所有権、副作用の境界が崩れ、無関係な変更や mock が必要になる。
- 重複実装、巨大関数、巨大ファイル、過剰な条件分岐により、変更時の見落としが起きやすい。
- public API や複数の caller が使う命名、型、戻り値、例外、状態管理が、実際の挙動を誤解させる。
- 単位、境界値、business rule、外部制約が名前や構造から読み取れず、誤修正につながる。
- コーディングガイドや既存パターンから外れており、将来の実装がぶれやすい。
- テストしづらい構造、mock しづらい依存、境界のない副作用がある。
- コメントやドキュメントが不足し、意図を保守者が追いにくい。

`P2` では、理想論だけを書かず、既存コードの近いパターンやガイドの該当箇所を根拠にする。
責務分離の指摘は、境界違反、知識の重複、異なる変更理由、不要な依存のいずれかを具体的に示す。
Readable Code の指摘は、複数の解釈、名前と挙動の不一致、変更漏れにつながる理解コストを具体的に示す。

## P3: その他の瑣末な点

`P3` は、取り込んでも大きな問題にはなりにくいが、直すと読みやすくなる点に使う。

- 表記ゆれ、軽微な命名改善、コメントの補足、ログ文言、型注釈の軽い改善。
- 単一関数内に閉じ、読み直せば誤解を解消できる変数名、式、制御フローの改善。
- 現時点では影響が限定的な TODO 化、follow-up 化、ドキュメント追記。
- 変更範囲外に近い改善提案、将来の拡張に備えた小さな整理。
- 明らかに未実装で落ちる箇所のうち、未実装であること自体が主要問題のもの。

未実装箇所は、`P1` として「落ちる」と責めるのではなく、`P3` として「TODO コメントを書く」「暫定実装であることを UI やコード上で明示する」「follow-up issue を切る」などの指摘にする。
ただし、未実装ではなく既存機能を壊す実装ミスであれば、通常どおり `P1` または `P2` を検討する。

## ランク決定の手順

1. 観測した事実、問題の解釈、具体的影響、最小の修正境界が揃っているか確認する。
2. 具体的な破綻経路があり、通常利用や既存機能を壊すなら `P1`。
3. 壊れ方は直接ではないが、保守性、可読性、責務、テスト容易性を損なうなら `P2`。
4. 影響が単一箇所に閉じ、理解速度だけを改善する軽微な整備なら `P3`。
5. 根拠が弱いものは指摘にせず、レビュー結論が変わる場合だけ確認事項へ移す。

## 指摘文の形

各指摘は次の要素を含める。

- 重大度: `P1` `P2` `P3`
- 主レンズ: `正しさ・契約` `責務分離` `Readable Code` `テスト容易性・規約`
- 根拠: ファイルパスと行番号、または差分内で一意に追える識別子
- 観測: 差分と関連実装で確認した事実
- 影響: 何が壊れるか、または保守時に何が難しくなるか
- 対照根拠: ガイド、既存パターン、call site、test のうち確認できたもの
- 修正方向: 最小限どう直すべきか
