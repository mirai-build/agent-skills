# 責務分離レンズ

PR 差分により責務の所有者や依存方向が崩れていないかを確認する必須レンズ。
ファイルや関数を細かく分けること自体を目的にせず、既存ガイド、変更影響、テスト容易性を根拠として、保守上の問題を指摘する。

## 実施ルール

- 変更ファイルを path 昇順、差分 hunk の出現順で確認する。
- 変更された入口ごとに、差分、呼び出し元、呼び出し先、近接する既存実装、関連テストを確認する。
- 差分外のコードは、変更で生じる影響と既存の責務境界を判断する範囲だけ読む。
- 各変更ファイルについて、確認した責務と判定を scratch に残す。問題がなくても確認を省略しない。
- 指摘候補はこのレンズで集め、重大度は全レンズの確認後に正規化する。

## 確認範囲

変更された関数、クラス、コンポーネント、hook、service、repository、endpoint、job を起点に、次を確認する。

1. **差分**
   - 追加・変更された判断、変換、副作用、状態、例外処理を特定する。
2. **呼び出し元**
   - 戻り値、例外、副作用、実行順序を誰が前提としているかを確認する。
   - 同じ処理を使う別経路に変更影響が及ぶかを確認する。
3. **呼び出し先**
   - DB、外部 API、filesystem、UI、framework などへの依存と、その抽象化の所有者を確認する。
4. **近接する既存実装**
   - 同じ feature、domain、画面、use case の配置・依存方向・命名と比較する。
   - `shared` や `lib` に置かれた処理は、複数箇所で再利用できる一般知識かを確認する。
5. **関連テスト**
   - 対象責務を単独で検証できるか、無関係な I/O や framework の mock が必要になっていないかを確認する。
6. **既存ガイド**
   - `AGENTS.md`、設計書、ADR、directory guide、README が責務や依存方向を定めていないかを確認する。

## 必須チェック項目

### 責務の混在

- 業務判断、データ取得、データ変換、永続化、表示整形、通知など、変更理由が異なる処理を同じ単位が所有していないか。
- orchestration と個別の業務ルールが混ざり、一方の変更だけでも全体を書き換える構造になっていないか。
- UI component や controller が domain rule、query、外部 API の詳細まで所有していないか。
- repository や gateway が表示文言、画面遷移、use case 固有の分岐を所有していないか。
- 汎用処理と feature 固有処理が同じ helper に入り、別 feature の都合で変更される構造になっていないか。

### 所有者と依存方向

- domain、feature、application、infrastructure、UI の依存が、既存ガイドや近接実装と逆向きになっていないか。
- feature 固有の型、文言、状態、業務判断が `shared` や `lib` に漏れていないか。
- 同じドメイン概念の検証、正規化、例外解釈を複数箇所が別々に所有していないか。
- 変更された処理が、呼び出し元にしか分からない前提や実行順序へ暗黙に依存していないか。
- 下位層が上位層の都合を知る callback、flag、framework 型を追加していないか。

### 変更影響

- 一つの仕様変更で、同じ判断を持つ複数箇所を同期して修正する必要がないか。
- 新しい分岐や引数が、既存責務を拡張するのではなく別の変更理由を持ち込んでいないか。
- 共通化により、本来独立して変更できる feature 同士が同じ実装へ結合していないか。
- 局所 helper の抽出や inlining により、意図、前提、副作用の境界が見えにくくなっていないか。
- ファイルサイズではなく、変更理由と所有する知識の数が増えていないか。

### テスト容易性

- 業務判断を検証するために DB、network、clock、乱数、UI framework など無関係な依存の mock が必要になっていないか。
- 副作用の発火条件と実行処理を別々に検証できる境界があるか。
- module-level state、singleton、global 設定により、テスト順序や実行環境へ依存していないか。
- private 実装の細部を再現しなければテストできず、公開契約から期待結果を検証できない構造になっていないか。
- 関連テストの配置と粒度が、近接する既存実装の責務境界と一致しているか。

## 指摘へ昇格する証拠要件

次の要件をすべて満たす候補だけを指摘事項へ昇格する。

1. **変更根拠**: 差分の行または変更された識別子を示せる。
2. **境界根拠**: 混在・逆流した責務を、既存ガイド、近接実装、依存方向、無関係な mock のいずれかから説明できる。
3. **影響根拠**: 修正漏れ、重複変更、誤用、調査困難、無関係な mock など、保守またはテスト上の具体的な不都合を示せる。
4. **修正境界**: 責務をどこへ戻すか、最小限の修正方向を示せる。

ガイドと近接実装が一致しない場合は、実際の呼び出し経路と関連テストを優先し、矛盾を確認事項として明示する。
将来の変更でのみ問題になる候補は、発生条件を具体化できなければ指摘へ昇格しない。

境界違反または同じ知識の重複を一つ確認できる場合は、指摘候補として検証を続ける。
それ以外は、異なる変更理由、責務外の依存、無関係な mock、状態所有者の重複のうち、二つ以上を確認できる場合だけ指摘候補として残す。

## 指摘しない条件

- 「分けた方がきれい」「この設計の方が好み」だけが理由である。
- ファイル行数、関数行数、引数の個数だけを根拠にしている。
- 一つの目的を達成する高凝集な処理を、形式的に別ファイルへ分ける提案である。
- 再利用箇所や独立した変更理由がない処理を、将来使う可能性だけで `shared` や `lib` へ移す提案である。
- 差分外に以前から存在し、今回の変更が問題を拡大も再利用もしていない。
- framework の標準構造やプロジェクト固有ガイドに沿った責務配置を、一般論だけで否定している。
- test double を使うこと自体を問題としており、テストの不安定化や責務外依存を示せない。
- 最小修正が PR の目的を大きく超える。必要なら残リスクまたは follow-up 候補として扱う。

## P2/P3 の目安

### P2

- 変更で責務境界または依存方向が崩れ、次の仕様変更で複数箇所の同期修正が必要になる。
- 業務判断の検証に無関係な I/O や framework の起動が必要となり、重要な分岐を単独でテストできない。
- feature 固有知識が共有層へ入り、別 feature がその都合へ結合する。
- 状態、例外、副作用の所有者が複数になり、呼び出し経路によって挙動や解釈がずれる。

### P3

- 影響が変更箇所内に限られ、誤用や同期修正の可能性が低い小さな配置・抽出の問題である。
- 既存ガイドとの軽微なずれはあるが、テスト容易性や依存方向を実質的に損なわない。
- 意図を示す短いコメントや局所的な命名整理で責務境界を明確にできる。

責務混在により具体的な実行時不具合が起きる場合は、このレンズだけで `P1` と決めず、正しさ・契約の確認結果と統合して重大度を判断する。

## 出力例

```markdown
- [P2][責務分離: 表示と業務判断] 価格判定を表示コンポーネントから domain 側へ戻してください
  - 根拠: src/features/cart/CartRow.tsx:48
  - 観測: 表示処理が会員価格の適用条件を所有し、同じ条件を API 用 mapper も別実装しています。
  - 影響: 価格条件の変更時に二箇所の同期修正が必要で、component test に価格ルールの全ケースが混在します。
  - 対照根拠: 同じ feature の送料判定は `ShippingPolicy` に集約されています。
  - 修正方向: 既存の `PricePolicy` に判定を集約し、コンポーネントは計算済み価格を表示してください。
```

確認結果には、指摘の有無にかかわらず対象件数を残す。

```markdown
- 責務分離: 変更 6 ファイル、入口 4 件、関連実装 3 件、関連テスト 5 件を確認。指摘 1 件。
```
