# ミライビルド PRレビュワー

## 概要

GitHub 上の PR またはローカルブランチ差分を対象に、コードレビューを日本語で行う。
対象リポジトリのコーディングガイドを先に読み、同じ手順を 3 パスで反復して、P1/P2/P3 の重大度つきで指摘事項を出す。

## 実行原則

- 既定ではレビュー専用として振る舞い、ユーザーが明示しない限りコード修正、整形、commit、push はしない。
- 出力は findings-first とし、指摘事項を重大度順に並べる。要約や良い点は指摘事項の後に置く。
- PR タイトル、PR コメント、レビューコメントを作る場合も日本語で書く。
- `P1` は明らかな不具合、実行時エラー、データ破壊、認可漏れ、ビルド失敗など、具体的な破綻経路を示せるものに限定する。
- `P2` は保守性、可読性、責務分離、テスト容易性、仕様追跡性の問題とする。
- `P3` は軽微な問題、表記ゆれ、コメント不足、将来対応、TODO 化すべき未実装箇所とする。
- 明らかに未実装で落ちる箇所は、それだけで `P1` にしない。`P3` として「TODO コメントを書く」「未実装であることを明示する」などの指摘にする。
- コーディングガイド、`AGENTS.md`、`README`、`docs/` 配下の開発規約を必ず確認する。見つからない場合は「確認できたガイドなし」と明示する。
- 3 パスのレビューを行い、最後に重複排除と重大度の正規化を行う。再実行しても同じ指摘になるよう、ファイル順、差分順、根拠行を安定させる。
- 推測だけの指摘を避ける。根拠が弱い場合は `P3` または確認事項へ下げる。

## 使う場面

- GitHub PR の URL、PR 番号、または `gh pr view` できる PR をレビューしたい。
- ローカルの作業ブランチと base ブランチの差分をレビューしたい。
- 変更内容について、明確な不具合、保守性、瑣末な改善を分けて指摘したい。
- コーディングガイドとの不一致を含めて、漏れの少ないレビュー結果を出したい。

## 基本フロー

1. 対象 repo、base、head、PR URL を確定する。可能なら `scripts/collect_review_context.py` で差分、commit、コーディングガイド候補を read-only で棚卸しする。
2. [`references/review_workflow.md`](./references/review_workflow.md) を読み、GitHub PR とローカル差分のどちらの入口で進めるかを決める。
3. [`references/severity_policy.md`](./references/severity_policy.md) を読み、P1/P2/P3 の判断基準を確定する。
4. コーディングガイド、プロジェクト固有ルール、変更差分、関連する実装元を読む。
5. 3 パスレビューを行う。
   - 1 パス目: 実行時エラー、不具合、データ破壊、認可漏れ、契約不整合など `P1` 候補を探す。
   - 2 パス目: 責務分離、可読性、保守性、テスト容易性、ガイド違反など `P2` 候補を探す。
   - 3 パス目: 軽微な改善、TODO 化すべき未実装、コメント不足、重複指摘、重大度のずれを確認する。
6. 指摘候補をファイルパスと行番号つきで重複排除し、重大度順に並べる。
7. 指摘事項、確認事項、テスト実行有無、残リスクを日本語で返す。

## 出力ルール

- 指摘がある場合は、最初に `指摘事項` を出す。
- 各指摘は `P1` `P2` `P3` のいずれかで始め、ファイルパス、行番号、問題、理由、修正方向を含める。
- 行番号が取れない場合でも、差分内の関数名、コンポーネント名、設定名など、追跡できる根拠を示す。
- 指摘がない場合は「指摘事項はありません」と明記し、確認した範囲と残リスクを短く添える。
- 実行したコマンド、実行できなかった検証、依存関係や認証不足で諦めた確認は最後にまとめる。
- inline code comment directive は、ユーザーが明示的に求めた場合だけ使う。
