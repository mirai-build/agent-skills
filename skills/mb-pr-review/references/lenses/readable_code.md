# Readable Code レンズ

このレンズは、Dustin Boswell、Trevor Foucher 著『リーダブルコード』の考え方を、PR で判定できる実務項目へ一般化したものである。
差分を初見の保守者が正しく理解するまでの時間を短くできるか確認する。
単なる好みではなく、誤読、変更漏れ、調査時間の増加につながる構造を指摘する。

## 適用範囲

- 変更された本番コードとテストコードを、ファイルごとに確認する。
- 差分だけで判断せず、名前の定義、呼び出し元、戻り値の利用箇所、近接する既存実装まで読む。
- 自動 formatter や lint が検出する表記だけで、このレンズの確認を終えない。
- 実際の不具合経路を発見した場合は、正しさの観点でも確認し、重大度ポリシーに従って判定する。

## 1. 命名を確認する

### 役割と具体性

- 変数名、関数名、クラス名から、対象と役割を一意に推測できるか。
- `data` `value` `item` `result` `info` などの広い名前が、複数の意味を隠していないか。
- 関数名が、取得、判定、変換、更新などの実際の処理を表しているか。
- 名前が実装詳細ではなく、呼び出し側が必要とする意味を表しているか。

### 単位、範囲、状態

- 時刻、期間、容量、金額、割合などで、`ms` `seconds` `bytes` `yen` `percent` の単位が分かるか。
- 開始・終了、上限・下限、含む・含まないなどの境界条件が名前から分かるか。
- 未処理、検証済み、同期中など、値が表す状態を読み違えないか。

### Boolean、単複、語彙

- Boolean は `is` `has` `can` `should` などを使い、真の場合の意味を肯定形で読めるか。
- 否定形の Boolean と否定条件が重なり、真偽を反転して読ませていないか。
- collection、単一要素、件数の名前が単複と一致しているか。
- 同じドメイン概念に同じ語彙を使い、同じ単語を別の意味に使っていないか。
- 略語はリポジトリで共有されており、初見の保守者が意味を特定できるか。

## 2. 制御フローを確認する

- 正常系が上から下へ追え、例外系や早期 return が主処理を隠していないか。
- 深いネスト、連続する `else`、複数の否定条件が分岐の意味を隠していないか。
- 条件の順序が、重要度、処理順、境界条件のいずれかで説明できるか。
- loop 内の `break` `continue` `return` や callback 内の脱出条件を見落としやすくしていないか。
- 複数の状態を暗黙に組み合わせ、到達可能な経路を把握しづらくしていないか。

## 3. 式と中間値を確認する

- 巨大な条件式、連鎖した変換、複雑な正規表現が、業務上の意味を隠していないか。
- 同じ部分式を繰り返し読み解く必要があり、変更時に片方だけ直す危険がないか。
- 意図を表す中間変数や小さな判定関数へ切り出すと、判断内容が明確になるか。
- 切り出しによって、処理順や副作用の有無が逆に分かりにくくならないか。

## 4. 変数の生存範囲を確認する

- 変数の宣言位置が利用箇所から離れ、途中で値が変わる可能性を追わせていないか。
- mutable な状態が必要以上に広い scope、長い期間、複数の関数にまたがっていないか。
- 一時値、cache、前回値、集計値の役割が混在していないか。
- class field や component state にする必要がない値を、長寿命な状態として保持していないか。

## 5. 関数の読みやすさを確認する

- 1つの関数内で、業務判断、データ取得、変換、永続化、表示整形など異なる抽象度が混ざっていないか。
- 関数名が約束する仕事を超えて、外部状態の更新や追加の問い合わせをしていないか。
- 引数、戻り値、例外から、呼び出し側が必要な前提と結果を理解できるか。
- Boolean 引数が呼び出し箇所の意味を隠していないか。名前付き引数、enum、関数分割で意図を示せるか。
- 小さな関数への分割が多すぎて、処理全体を追うために不要な往復を強いていないか。

## 6. 副作用を確認する

- 名前から読み取れない DB 更新、network I/O、file I/O、log、通知、global state 更新がないか。
- 値の取得と状態変更を同時に行い、呼び出し順によって結果が変わらないか。
- 副作用の実行条件、順序、失敗時の扱いを呼び出し側から追えるか。
- mock を大量に読まないと主要な振る舞いが分からない構造になっていないか。

## 7. コメントを確認する

- コメントがコードの言い換えではなく、制約、理由、選択しなかった案、外部仕様を説明しているか。
- コード変更後も正しい内容であり、古い名前や挙動を説明していないか。
- 複雑なコードをコメントで補う前に、命名や構造で意図を表せないか。
- TODO は未完了内容、必要な条件、issue などの追跡手段を示しているか。
- public API や非自明な処理は、利用者が誤用を避けるために必要な情報を示しているか。

## 8. テストの可読性を確認する

- テスト名から、前提、操作、期待結果を特定できるか。
- setup、実行、検証の境界が分かり、重要な入力値が fixture の奥に隠れていないか。
- assertion が振る舞いを直接表し、無関係な値や巨大な snapshot に依存していないか。
- helper の名前と引数から、テスト固有の条件を読み取れるか。
- 複数の振る舞いを1つのテストに詰め込み、失敗理由を特定しづらくしていないか。
- 本番コードの内部手順ではなく、保護したい契約や結果を検証しているか。

## 指摘を成立させる証拠

候補を指摘にする前に、次の4点を説明する。

1. 差分または関連コードで確認できる事実。
2. 読み手が取り得る誤解、または追跡が必要になる複数の解釈。
3. 誤修正、変更漏れ、調査困難などの具体的な保守上の不都合。
4. 問題を解消する最小限の修正境界。

根拠には、差分の行番号と、必要に応じて呼び出し元、型、テスト、既存の近いパターンを含める。
将来の可能性だけを根拠にせず、現在の差分で発生している読みづらさを示す。

## 指摘にしない条件

- 意味が同程度に明確な名前や書き方の選好だけである。
- リポジトリで統一されていないスタイルを、個人の流儀だけで要求している。
- formatter、lint、自動修正だけで完結し、レビューで伝える追加価値がない。
- 差分外の全面的なリファクタリングが必要で、今回の変更による悪化を示せない。
- 抽象化や共通化による具体的な読みやすさの改善を説明できない。

好みとの差を述べるだけの候補は破棄する。結論に影響する不明点があれば、指摘ではなく確認事項へ移す。

## 重大度の目安

- `P2`: 名前と実際の副作用が異なる、複数の責務や抽象度が混在する、複雑な条件や広い mutable state が変更漏れを誘発するなど、具体的な保守リスクがある。
- `P3`: 誤解の範囲が局所的な名前、補足すると意図が明確になるコメント、限定的なテスト名など、小さな修正で読みやすさが改善する。
- 実害が説明できない場合は重大度を下げるのではなく、指摘から除外する。

## レンズの完了条件と出力例

変更ファイルごとに各項目を確認し、指摘がない場合も確認件数を残す。

```markdown
観点別確認結果
- Readable Code: 本番コード5ファイル、テスト2ファイルを確認、指摘1件

- [P2][Readable Code: 名前と副作用] `loadUser` が取得と既読更新を同時に行う
  - 根拠: src/features/user/loadUser.ts:24
  - 観測: 取得だけを期待する呼び出しでも既読状態が更新される。
  - 影響: 関数名から副作用を判断できず、呼び出し追加時に状態変更を見落とします。
  - 対照根拠: 既存の `markUserAsRead` は更新処理を名前で明示しています。
  - 修正方向: 取得と既読更新を分け、更新処理を呼び出し側で明示する。
```
